# 集成调研 · 把 dsh-pet 的动画素材与桌宠交互接进鲸记

> 调研时间：2026-09-20 · 结论：**技术上完全可行，但有一个硬约束（素材许可）和一个硬取舍（体积）需要先定**
> 本文是给下一轮对话的交接材料：读完这一份就能直接开工，不必重新调研。

---

## 0. 一句话结论

dsh-pet 的素材是 **640×360 / 24fps / VP9-alpha 透明 WebM**（106 个动作）；
鲸记能吃的只有 **720×720 精灵图 PNG**。两头对不上，中间必须做一次**离线转码**——
而这条转码链**本机已经实测跑通**（见第 4 节），不需要联网、不需要装系统级 ffmpeg。

真正的问题不是"能不能转"，而是三件事：

1. **许可**：素材是 CC BY-NC-SA 类同人素材，**只能个人非商业用**，必须署名（第 2 节）。
2. **体积**：106 个动作全转 ≈ **1.4 GB**，会把这个 58 MB 的便携包撑爆（第 6 节）。
3. **范围**：交互逻辑是 Python/Qt 的，**不能照搬**，只能把行为参数用 C# 重写（第 7 节）。

## 4. 技术验证：转码链已经跑通（含一个坑）

### ✅ 可行路径

```bash
ffmpeg -c:v libvpx-vp9 -i <输入>.webm -pix_fmt rgba <输出>_%04d.png
```

实测结果（本机，2026-09-20）：

```
ffmpeg 7.1（含 --enable-libvpx）
frame_01.png: RGBA (640, 360)  alpha min 0 max 255
  → 透明 82.9% / 半透明像素 191513 / alpha 层级 255
```

**alpha 完整保留，羽化边缘 19 万个半透明像素都在。**

### ❌ 踩到的坑：PyAV 会静默丢 alpha

先装的 `av`（PyAV 18.1.0）解出来是 **`yuv420p`，alpha 全是 255**——
文件里明明有 `ALPHA_MODE=1`。`to_ndarray('rgba')` / `'bgra'` 都一样，
`'yuva420p'` 直接报 `Conversion to numpy array with format yuva420p is not yet supported`。

**结论：别用 PyAV 干这件事，它内置的 ffmpeg 构建不走 VP9 的 alpha 辅助流。**
用 imageio-ffmpeg 提供的**真 ffmpeg 二进制**（`imageio_ffmpeg.get_ffmpeg_exe()`）。

### 本机环境（已就绪，无需再配）

| 组件 | 状态 |
|---|---|
| `ffmpeg.exe` | 无系统级安装，但 **`imageio-ffmpeg` 自带 7.1**（venv 内），已验证可用 |
| `PyAV` | 已装但**不要用于取 alpha**（见上） |
| `Pillow` / `numpy` | venv `default` 里已有（12.3.0 / 2.5.3） |
| Python | 用 `C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe` |

## 5. 目标格式：鲸记的精灵图规格

全在 `docs/动态素材规格.md`，这里只摘要点（**别重复造轮子，转码脚本要遵守它**）：

| 项 | 值 |
|---|---|
| 每格画布 | **720 × 720** |
| 角色高度 | **600 px**（与现有本体一致，屏幕上大小不变） |
| 横向中心 | **x = 360** |
| 脚底基线 | **y = 660** |
| 硬规则 | 每帧的横向中心与脚底必须落在同一点；横向**绝不能左右漂**（允差 2px） |
| 容器 | **精灵图 PNG + sheet.json**（GIF/APNG/WebP 都实测被否，见规格第 6 节） |
| 存放 | `Assets\anim\<动作名>\sheet.png` + `sheet.json` |

**这意味着转码要把 640×360 的源帧做三步几何变换**：

1. 按 alpha 包围盒裁出角色（源里角色只有 213×267）
2. 等比放大 2.247 倍 → 宽 479 × 高 600
3. 贴到 720×720 画布：横向居中（x 中心 360）、脚底对齐 y=660

> ⚠️ 第 3 步的"脚底"用固定值 **660**，但源素材里角色脚底会随动作上下移动
> （跳跃、伸展）。**必须让"静止态脚底"对齐 660**，而不是逐帧对齐——
> 逐帧对齐会把跳跃整个压平，动感全失。建议用 `body_box`（y=330）
> 对应的源坐标做锚点，按同一变换矩阵套用到每一帧。

## 6. 体积测算与取舍（必须用户定）

实测（同一帧内容，8 帧横向拼图后均摊）：

| 量 | 值 |
|---|---|
| 源帧 640×360 PNG | 115 KB |
| 放大贴到 720×720 后的**单张** PNG | 361 KB |
| 拼成精灵图后**每帧均摊** | **58 KB**（PNG 对相似帧压缩率极高） |
| 单动作（241 帧） | **≈ 13.7 MB** |
| 全部 106 个动作 | **≈ 1.42 GB** ❌ |

对比现状：鲸记整个便携包才 **58 MB**。全量集成会让它涨到 1.4 GB+，不现实。

### 三个可选档位

| 档位 | 动作数 | 预估体积 | 便携包总计 | 说明 |
|---|---|---|---|---|
| **精简（推荐先做）** | 8 个 | ≈ 110 MB | ≈ 165 MB | idle + turn + click×5 + drag |
| 标准 | 11 个 | ≈ 150 MB | ≈ 205 MB | 再加 move×3（会走动的桌宠） |
| 精选合集 | 20~25 个 | ≈ 280~340 MB | ≈ 340~400 MB | 再从 random 里挑最出彩的 |

进一步省体积的两条路（可叠加）：

- **降帧率到 12fps**（抽帧）→ 体积**减半**，桌宠动画基本看不出差别。
- **只对"每帧都在动"的动作保留全帧**，静态待机类抽帧更狠。

## 7. 交互模块：能移植什么、不能移植什么

源项目是 **PySide6/Python**，鲸记是 **WPF/C#**——**代码一行都不能直接搬**，
能搬的是**行为设计与参数**。`pet/catalog.py` 里这些常量可直接对应成 C# 常量：

| 源常量 | 值 | 含义 |
|---|---|---|
| `P_IDLE / P_TURN / P_ACTS` | 0.30 / 0.40 / 0.80 | 动画链概率：30% 待机、10% 转向、40% 动作、20% 移动 |
| `MOVE_MIN_PX / MOVE_MAX_PX` | 60 / 240 | 一次移动的距离区间 |
| `MOVE_MARGIN` | 20 | 屏幕边缘安全边距 |
| `MOVE_LEAD_SEC / TAIL_SEC` | 2 / 2 | 移动动画头尾各 2s 是准备/收尾，位置不动 |
| `DRAG_THRESHOLD` | 5 | 拖拽判定阈值（px） |
| `DEFAULT_SCALE / SCALE_STEPS` | 0.72 / (0.5, 0.72, 0.85, 1.0) | 显示缩放档位 |
| `CORNER_MARGIN` | 24 | 距屏幕右缘的默认间距 |

### 交互能力对照表

| dsh-pet 的能力 | 鲸记现状 | 移植难度 | 建议 |
|---|---|---|---|
| 待机呼吸 / 随机小动作 | 有（眨眼 + 4~9s 随机） | 低 | ✅ 换成 dsh 素材即可 |
| 点击回应（5 种随机） | 有（点击弹一下） | 低 | ✅ 直接升级 |
| 拖拽时播"悬空反馈" | 有拖拽 | 低 | ✅ 加上拖拽态动画 |
| **自主走动**（左右移动 ±60~240px） | ❌ 无 | **中** | ⭐ 最有价值的新能力 |
| **贴边吸附 / 屏幕边缘约束** | ❌ 无 | 中 | ⭐ 随走动一起做 |
| 气泡说话 / 情绪文案 | 有气泡 | 低 | 可接 |
| 多实例碰撞 IPC（两个桌宠相遇） | ❌ 无 | **高** | ❌ 不建议做，收益低 |
| 余额事件（events/balance 6 个） | — | — | ❌ 鲸记没有"余额"概念，无意义 |
| 上下文菜单 / 设置系统 | 鲸记已有自己的 | — | ❌ 不移植 |

> **一句话：值得移植的是"形象 + 点击/拖拽/待机 + 自主走动"这一层；
> dsh-pet 的菜单、设置、IPC、余额事件都不属于本次范围。**

# 落地结果（2026-09-20 已实施，版本 1.4.0；当天下午补丁 1.4.1 → 1.4.2 → 1.4.3 → 1.4.4）

上面第 1~9 节是**开工前**的调研与方案。真正做下来有几处结论被实测推翻了，
下面是最终落地的样子 —— **要以这一节为准**，前面几节当过程记录看。

## 11.1 与方案最大的分歧：不转精灵图，改成运行时解码

方案里估的"全量 106 个动作 ≈ 1.42 GB"，实测下来实际是 **1.82 GB**
（384×384 格子、24fps 全帧）。降帧率只省 32%，不是预估的一半 —— 因为
106 个动作里有相当一部分**每一帧都在动**，抽帧就是抽信息。

挖到根因之后方案整个换了：

| | PNG 精灵图 | 源素材 VP9-alpha |
|---|---|---|
| 压缩率 | 约 **3 倍** | 约 **100 倍** |
| 106 个动作 | 1.82 GB | **51.9 MB** |

差距不在"帧数"也不在 alpha 通道（RGB 占 86%，alpha 不是瓶颈），
而在于 **VP9 的帧间预测**：这类连续画面用 PNG 逐帧存是纯粹的浪费。

所以最终方案是 **原样搬运 webm，运行时用 ffmpeg 解码**：

- 素材**一个字节都不重新编码** → 画质与源素材逐像素相同（用户明确要求"不要精简"）
- 便携包从 58 MB 涨到 **139.6 MB**（多出来的是 52 MB 素材 + 84 MB 的 `ffmpeg.exe`）
- WPF 自己解不了 VP9 的 alpha 通道，所以 ffmpeg 是**必需的外部依赖**

## 11.2 实测的性能数字（决定架构的就是这几个数）

| 量 | 实测值 | 影响 |
|---|---|---|
| 241 帧全量解码耗时 | **0.38 s**（≈640 fps，26 倍实时） | 解码远快于播放，可以边播边解 |
| 一帧的原始大小 | **576 KB**（384×384 RGBA） | 整个动作 142 MB，**放不进内存** |
| ffmpeg 冷启动 | **约 150 ms** | 每次起播的固定延迟 → 需要"预热" |

推论：
1. 一帧都不能预存 → **流式解码 + 小环形缓冲**（8 帧 = 4.6 MB）
2. 解码比播放快 26 倍 → 不需要 `-re`，让**缓冲水位**卡住 ffmpeg 即可
   （缓冲满了 ffmpeg 自己阻塞在写管道上，天然不积压、几乎不吃 CPU）
3. 150 ms 的启动延迟对"点一下要有反应"太慢 → 鼠标**移进悬浮窗时就预热**
   （提前起好 ffmpeg、把前 8 帧解到手，点下去直接播）

## 11.3 最终架构（新增/改动的文件）

| 文件 | 职责 |
|---|---|
| `assets/characters/dsh/` | **出厂形象包**（106 动作 / 25423 帧 / 51.9 MB）。仓库里这份是唯一来源，打包时原样拷进 `Assets\characters\dsh\` |
| `tools/fetch_dsh_assets.py` | 从 GitHub 拉源素材（走 jsDelivr CDN 镜像，见 11.6） |
| `tools/convert_dsh_webm.py` | 生成形象包：拷 webm + 写 `anim.json` + 用同一滤镜抽静态首帧；`--probe/--bench/--emit/--check` 四个子命令 |
| `Services/VideoDecoder.cs` | `VideoFrameStream`：ffmpeg 子进程 + 环形缓冲 + 读帧线程 + stderr 排空线程。`TryTake/Return/IsDrained` |
| `Services/FfmpegLocator.cs` | 找 `ffmpeg.exe`（程序目录 → 素材目录 → 工具目录 → PATH），缓存 |
| `Services/CharacterPacks.cs` | 形象包：`Resolve`（永远返回一个能用的形象）/`DirOf`/`Discover`/`Available` |
| `Services/AnimSheet.cs` | 帧表支持 `type:"video"`；**滤镜串当不可信输入校验**（防命令注入） |

## 11.11 补丁 1.4.2：用户报「运行时颜色不对，锯齿很严重，还有黑底」

**这是 dsh-pet 这条路线最隐蔽的一个坑 —— 而且和调研阶段记下的「PyAV 静默丢 alpha」
是同一个东西，只是换了个马甲。**

### 现象与根因

用户贴的截图里，形象**顶着一个黑色方块**，边缘像被剪刀剪过。
看着像"配色错了"，实际是**alpha 通道整个没了**：透明区变成了不透明黑，
原本羽化的边缘变成了硬边（所以看着"锯齿严重"）。

根因不在代码逻辑，在**解码器的选择**：

透明 webm 的 alpha 不是普通像素，而是 VP9 的**附加数据**
（matroska `BlockAdditional`；`ffmpeg -i` 的输出里明明白白写着 `ALPHA_MODE: 1`）。
ffmpeg 默认挑的 **native vp9 解码器不认这层附加数据** ——
它照样一帧帧给你像素，只是 alpha 位全填 255，而且**不报任何错**。

### 实测数据

`idle-待机呼吸休闲`（640×360 源 → 384×384 格子，241 帧）：

| 解码器 | 报告的输出像素格式 | alpha 直方图 | 全解耗时 |
|---|---|---|---|
| native vp9（默认） | `yuv420p` | 255 占 **100%** | 0.155 s |
| `libvpx-vp9`（点名） | `yuva420p` | 0 与 255 各占约 50% | 0.183 s |

修复就是加一行**输入侧**选项（必须放在 `-i` 前面）：

```bat
-c:v libvpx-vp9
```

**代价 18%**（0.155 → 0.183 秒），而解码本来就跑在实时的 60 倍上，
对环形缓冲的水位毫无影响。

### 顺手排除掉一个错误方向

"颜色不对"这个描述很容易让人往**色彩空间**（`bt709` / 色彩矩阵 / full-range）上想。
实测把两种解码器解出的帧**逐像素比对**：完全实心（alpha=255）的 36269 个像素，
平均 RGB 都是 `(100.53, 108.03, 144.30)`，**单像素最大差值 0**。

所以颜色一个字节都没错 —— 观感上的"色偏"完全是黑底造成的对比错觉。
**先测，再猜。** 当时要是顺着色彩空间去改，会把一条已经正确的链路改坏。

### 测试为什么没抓住（真正的教训）

旧自检对视频**只断言了两件事**：解出多少帧、每帧多少字节。
而 alpha 全丢的情况下这两条**全部通过** —— 黑底就这样一路混进了 1.4.0 和 1.4.1
两个出厂包，直到用户肉眼看见。

新加的检查换了思路：**数像素内容，不数结构**。
现场用 ffmpeg 造一段 `geq=r='255':g='0':b='0':a='if(lt(X,32),255,0)'`
的 VP9 素材（左半不透明、右半全透明），解码后**逐像素统计 alpha**，
有 `alpha==0` 的像素才算过。

并且做了**反向验证**：把 `UsingLibvpx` 强行置 false 重新编译，自检立刻在新增断言里
挂掉 3 条（`全透明 0/4096 个像素 —— alpha 整条丢了`），改回来即全绿。
**能失败的测试才算测试。**

### 和 11.9 那个 bug 是同构的

11.9 第 1 条是"滤镜串解析错了，106 个动作全被拒收"，
这一条是"解码器选错了，106 个动作的 alpha 全丢"。
两次都是**链路上有一个静默的环节做了错误选择，而它不报错**。
所以：凡是有"像素级正确性"要求的环节，断言必须落到**内容**上。

## 11.12 补丁 1.4.3：用户报「颜色还是不对，像反色了，本来应该是蓝色」

上一条刚把黑底修掉，用户紧接着报：黑底是没了，但**颜色整个是错的** ——
深蓝紫的头发显示成栗棕红、眼睛从蓝变橙。而且给了一条关键线索：

> 「目前只有切换的时候开头几帧是对的」

### 那条线索差点把方向带偏

通道顺序这种错是**逐帧一致**的，如果真是它，应该每一帧都错，
不可能"开头对、后面错"。于是先去查"逐帧累积的损坏"：
帧边界漂移？环形缓冲被覆写？

读 `VideoDecoder.ReaderLoop` / `ReadExact` 才排除掉 —— 它是
`while (got < count)` **读满一整帧**的，帧边界不会漂。

真正的解释很简单：**切换动作后的那几帧根本不是视频帧**，
是 WPF 自己解码的**静态图**（`whale.png`，那张是准的）；
视频帧要等 ffmpeg 起来（≈150 ms）之后才贴上。
所以"开头几帧对"和"逐帧一致的通道错误"**并不矛盾** —— 是两段不同的东西。

### 根因：裸字节的字节序没对齐

| 一侧 | 字节序 |
|---|---|
| `-pix_fmt rgba`（改之前） | R, G, B, A |
| WPF `PixelFormats.Bgra32`（`SpritePlayer` 贴图用的） | **B, G, R, A** |

两个名字看着都在说"红绿蓝"，但一个说的是**分量顺序**、一个说的是**内存顺序**，
差一格就是**红蓝两条通道整个对调**。中间没有任何代码做转换 ——
解码器给的是裸字节，取出来直接 `WritePixels` 贴上去。

### 实测数据

同一帧，`-pix_fmt rgba` 的原始字节 vs ffmpeg 自己编码的 PNG：

| 解读方式 | 最大差值 | 超阈值像素通道数 |
|---|---|---|
| 按 R,G,B,A | **0** | 0 |
| 按 B,G,R,A | 125 | 76306 |

界面级铁证（同一张 `--shot-floating` 截图里数特定颜色）：

| 图 | 蓝紫发色像素 | 栗棕红像素 |
|---|---|---|
| `whale.png` 静态图（WPF 自己解码 → 基准） | 1160 | **0** |
| 修复前那张悬浮窗截图 | 1728 | **299** |
| 修复后 | 2027 | **0** |

同一张图里**静态图是蓝的、视频帧是棕的**，而且 1728 + 299 = 2027。
上一轮把这张图里的角色描述成"棕发"时其实已经看到了 bug，
只是误当成"不同姿势"放过去了。

### 修法

```bat
-pix_fmt bgra          :: 不是 rgba！和 PixelFormats.Bgra32 的内存序对齐
```

swscale 内部顺手就换，**不额外花时间**。C# 侧一个像素都不用动。

### 测试为什么又没抓住

上一节补的「数透明像素个数」检查在**颜色全反**的情况下**照样全过** ——
因为它只看第 4 个字节（alpha）。所以这次在同一节里追加**通道序断言**：
素材左半边本来就是纯红，正好拿来验"红值有没有落在 R 通道上"。

反向验证：把 `PixelFormat` 强行改回 `"rgba"` 重编 ——
自测 303 通过 / 2 失败、自检 1 项未通过，报的是
`R=0 G=0 B=253 —— 红蓝反了`。改回来即全绿（自测 305、自检 208 项 / 21 段）。

### 教训（这条比 bug 本身值钱）

**"解出来了"和"解对了"是两回事。**

- 1.4.2 之前的断言：帧数对不对、每帧字节数对不对 → alpha 全丢时**全过**；
- 1.4.2 补的断言：有没有透明像素、有没有实心像素 → 颜色全反时**全过**。

两次都是"结构对了、内容错了"。所以断言要落到**画面内容**上：
透明值有多少、**红值落在哪条通道**。
另外：**用户说的每一句现象都要当真**（"像反色""开头几帧是对的"），
它们是定位的关键证据，不是修辞。

## 11.13 功能 1.4.4：把文件直接拖到小鲸鱼上归档（2026-09-20）

用户提的需求，和形象无关，但**改的正是同一个悬浮窗**，所以记在这里。

**需求**：「可以直接把文件拖到悬浮窗上然后自动打开主页面并归档」。

**做法**：入口接在 `FloatingWindow` 上，链路完全复用主面板那套 `FileIntakeService`
（分类规则 / 版本判定 / 原文件保护一个字都不改）。悬浮窗只多做两件事：
把主面板支起来并切到「文件归档」页、把结果弹成气泡。归属日期**一律今天**，
和主面板当时在翻哪一天无关。

**唯一的难点：透明的地方接不住拖放。**

悬浮窗是 `AllowsTransparency="True"` 的层叠窗口 —— Windows 对这类窗口的命中测试
**逐像素看 alpha**，alpha = 0 的像素上 OLE 拖放会直接穿透到下层窗口。
于是把文件拖到鲸鱼**旁边**的空白处，什么都发生不了，而且**不报任何错**；
鲸鱼本体上却是好的 → 表现成"这个功能时灵时不灵"。

修法：根 `Grid` 的背景从 `Transparent`（alpha = 0）改成 **`#01000000`**（alpha = 1 的近透明黑）。
肉眼无差别，但整块矩形都变成可命中的了。

**为什么这一条断言测不出来**：`DragEventArgs` 的构造函数是 internal，造不出假事件，
处理函数全对、命中测试全错，自检会"全绿"。所以补了一条**真实的 OLE 拖放探针**：

- `tools/dragsource/`：C# 写的真实拖拽源，在自己的 `MouseDown` 上下文里发起 `DoDragDrop`
  （按下点必须用 `PointToScreen` 算屏幕坐标 —— 用 DIP 的 `Left/Top` 在高 DPI 屏上会按到
  窗口外面，`DoDragDrop` 直接挂死）。
- `tools/drop_probe.py`：三个场景 —— 拖到鲸鱼**旁边**（该接住，就是这条的哨兵）、
  拖到鲸鱼**身上**（该接住）、拖到窗口**矩形外**（不该接住）。
  判据只看"主面板开没开 + 文件进没进当天归档"，**不看 `DoDragDrop` 的返回值**
  （桌面也是合法拖放目标，`effect` 恒为 `Copy`，看它会假绿）。

**验证**：三场景连跑两轮全绿；**反向验证**——背景改回 `Transparent` 重跑，
透明区确实接不住、主面板不弹、不归档（证明修复有效且有牙）。
自检新增「悬浮窗的文件拖放」一节 9 项断言：为了验"一律记到今天"，
探针会**先把主面板拨到昨天**再拖（不翻走的话主面板恰好就在今天，这条规则测不出来）。
自检 **217 项 / 22 段全过**、自测 **312 项全过**，探针写进库的记录结束时原样撤回。

**顺带修掉的一个老 bug**：`FileIntakeService.Expand` 过滤自己数据目录时前缀比较没补目录分隔符，
导致**名字以数据目录名开头的兄弟目录被整批静默跳过**。已修 + 加自测。
（发现它纯属偶然：探针的测试文件造错了位置，现象是"接住了但归档 0 条"。）

**教训**：**"窗口接住了没有"和"处理函数对不对"是两回事。**
前者靠运行时环境（命中测试、DPI、模态循环）决定，只能真跑一次，
而且必须配一个反向验证 —— 否则"探针有牙"只是自欺。
另外：**透明的窗口不是"看不见的窗口"，是"没长在那儿的窗口"** ——
它同时管着视觉和命中测试，以后给悬浮窗加交互先问一句"这块像素是不是全透明"。
