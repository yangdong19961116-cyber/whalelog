## dsh-pet 集成调研（未改主程序）

用户提出把 `MerZlin/dsh-pet-indesktop` 的动画素材与桌宠交互接进鲸记。
本轮只做可行性验证与方案，产出：

- `docs/dsh-pet-集成方案与调研.md` —— 完整方案（结论 / 许可 / 规格 / 体积 / 实施顺序 / 待决策）
- `docs/dsh-pet-调研附件/` —— 样本 webm + manifest + 解帧 PNG + 体积实测件（不联网可复现）

### 技术结论（全部实跑）

- 源素材：640×360 / 24fps / **VP9-alpha 透明 webm**，106 个，共 52 MB，角色仅 213×267。
  源自 `PC2005-cloud/dsh-pet`；本项目是 PySide6 桌面应用，代码 MIT。
- 鲸记只吃 **720×720 精灵图 PNG**（`docs/动态素材规格.md` 第 6 节实测否掉了 GIF/APNG/WebP）。
- 转码链：ffmpeg 解 RGBA 帧 → 裁角色 → 放大 2.247× → 贴 720×720（中心 x=360、脚底 y=660）。
- 体积：全量 106 个 ≈ **1.4 GB**（便携包现在才 58 MB）；精简 8 个 ≈ 110 MB；抽到 12fps 再减半。

### ⚠️ 两个必须记住的坑

1. **PyAV 会静默丢 alpha。** `av` 解这个 webm 得到 `yuv420p`、alpha 全 255，
   而文件 stream metadata 里明明有 `ALPHA_MODE=1`。`to_ndarray('rgba')`/`'bgra'` 都无济于事，
   `'yuva420p'` 直接报 `Conversion ... is not yet supported`。
   → **取 alpha 只能走 `imageio-ffmpeg` 自带的 ffmpeg 二进制**（本机没有系统 ffmpeg，
   但那个包里的 7.1 含 libvpx，实测能解出 256 级 alpha）。
2. 源项目的 Release 资产（140~270 MB 的 exe/zip）是**打包好的应用，不是素材源**；
   素材要去源码仓库的 `assets/characters/shenshen/videos/` 拿。

### 许可硬约束

素材是 CC BY-NC-SA 类同人素材（OC「溟月」/ 画师上善无形），**仅限个人非商业使用，必须署名**。
鲸记自用没问题；一旦要发布或商用，这批素材及由其生成的动画必须整体撤下。

### 交互模块

PySide6/Python 代码不能直接搬，能搬的是行为参数（`pet/catalog.py` 里：动画链概率、
移动距离 60~240px、拖拽阈值 5px、缩放档位等）。真正值得新增的能力是**「自主走动 + 贴边」**——
鲸记目前完全没有。菜单/设置/IPC/余额事件都不在范围内。

### 待用户决策

许可是否接受 / 体积档位 / 是否抽帧到 12fps / 形象替换还是共存 / 要不要做自主走动。

## dsh-pet 落地（同一天紧接着做完，1.3.2 → **1.4.0**）

用户在 5 个点上拍板：**接受许可**（个人非商业 + 界面署名）、**所有素材都要不精简**、
**形象替换成新的但给旧版留切换开关**、**不做自主走动**、**但要贴边**。

### 路线改了：不转精灵图，改成运行时解码

调研时算的是「全量转 720×720 精灵图 ≈ 1.4 GB」。真做的时候换成
**透明 webm 原样搬运 + 运行时 ffmpeg 逐帧解**：

| | 结果 |
|---|---|
| 素材包 | 106 动作 / 25423 帧 / **51.9 MB**（原样搬运，零重编码，画质与源素材一致） |
| 解码开销 | 解 241 帧 0.38 s；边解边放 142 MB 内存峰值；起一次 ffmpeg ≈ **150 ms** |
| 便携包 | 58 MB → **139.6 MB**（+52 MB 素材 +84 MB ffmpeg.exe，两者都压不动） |

关键设计（都写在 `Services/VideoDecoder.cs` 的注释里）：
**8 帧环形缓冲**（满则阻塞生产者 → 天然不积压、几乎不吃 CPU）、
**鼠标移入悬浮窗就预热**（`SpritePlayer.Warm`，抵掉 150 ms 冷启动）、
**时间驱动取帧、一个 tick 最多贴一帧、落后逐帧追但绝不快进**。

### 形象包

`Assets\characters\<形象ID>\` 一套形象一个目录；`classic` 是保留名，根目录就是 `Assets\` 本身
（**原版没搬家**，老用户往 `Assets\` 放过的图照样有效）。
`CharacterPacks.Resolve` 降级顺序 **设置里那个 → dsh → classic**（原版是嵌入资源、永远能用）。

### 贴边

吸附改成**两轴独立判定**（能吸到角上），关掉吸附也记方向。**按用户决定没做自主走动。**

### 两个新踩的坑

1. **`AnimSheet.ValidateFilter` 把分隔符认错**：先按 `:` 切会把 `crop=384:360:128:0` 的
   **滤镜名**切成 `crop=384` → **106 个动作全被拒收**，界面表现只是"动画一个都不出来"。
   正确顺序是**先按 `=` 切名字、再按 `:` 切参数**，位置参数只放行数字、具名参数走白名单。
   这个 bug 是自测抓出来的。
2. **打包脚本的"暂存目录"会被异步回收**（最坑的一个）：
   受限环境拦「一次删 50+ 文件」并要人工确认，**被拦下的删除请求会在后台被逐个补执行** ——
   打包期间它把暂存树里的 `Assets\` 以约 **17 个/秒**匀速啃掉，
   于是包变成**「程序在、素材没了」**，而脚本自己**一句报错都没有**。
   定位方式：脚本里加采样线程看到 465 → 244 匀速下降；同时发现
   `build\asset-probe-data` 从 841 个文件被削到 3 个，才确认是那个机制。
   → **改成不落暂存目录**（生成的两份 json 用 `writestr`，出厂素材导到系统临时目录，
   形象素材直接读源目录进 zip），并且**落盘后回查关键条目**，缺一条就非 0 退出。

### 顺带修正的一处认知

`dotnet restore` 报 `Value cannot be null (Parameter 'path1')` 一直被认为是"受限会话做不到"，
真因只是 **shell 拿不到 Windows 会话的环境变量**（`ProgramData` / `APPDATA` 缺失）。

## 补丁 1.4.2：用户报「运行时颜色不对，锯齿很严重，还有黑底」（同一天下午）

**现象**：用户贴了一张悬浮窗截图 —— 形象**顶着一个黑色方块**，边缘生硬。
看着像"配色错了"，实际是**整个 alpha 通道没了**。

**根因**：`VideoDecoder.cs` 起 ffmpeg 时没点名解码器，ffmpeg 默认挑 **native vp9**，
而它**不认 VP9 的 alpha 附加数据**（matroska `BlockAdditional`；`ffmpeg -i` 里写着 `ALPHA_MODE: 1`）。
它照样一帧帧吐 RGBA，只是 **alpha 位全填 255** —— 透明区成了不透明黑，羽化边缘成了硬边。
**全程不报任何错**，所以看日志、数帧数永远发现不了。

实测（`idle-待机呼吸休闲`，640×360 → 384 格子，241 帧）：

| 解码器 | 输出像素格式 | alpha 分布 | 全解耗时 |
|---|---|---|---|
| native vp9（默认） | `yuv420p` | 255 占 **100%** | 0.155 s |
| `libvpx-vp9`（点名） | `yuva420p` | 0 / 255 各约一半 | 0.183 s |

**修了三处**：

1. `VideoDecoder.cs`：`IsVp9Webm`（读文件头 64 KB 搜明文 `V_VP9`，不起进程）+
   `FfmpegSupportsVp9Alpha`（问一次 `-decoders` 后缓存）；两条都满足才在 `-i` **之前**加
   `-c:v libvpx-vp9`。新增 `IsVp9Source` / `UsingLibvpx` / `HasAlpha` 三个诊断属性。
2. `DiagnosticsService.cs`：新增 `ProbeVideoAlpha` —— 现场造一段左半不透明、右半全透明的
   VP9 素材（`geq=r='255':g='0':b='0':a='if(lt(X,32),255,0)'`），解一帧**逐像素数透明值**，6 条断言。
3. `tools/selftest/`：新增 `TestVideoAlpha`，9 条断言 —— **自测 294 → 303**。

**自检 195 → 207 项**（21 段不变；隔离空数据时 201；再有实例在跑 206）。

**顺手排除了一个错误方向**：看到"颜色不对"很容易往色彩空间（bt709 / 矩阵 / range）上想。
实测把两种解码器解出的**实心像素逐像素比对：单像素最大差值 0** —— 颜色一个字节都没错。
观感上的"色偏"完全是黑底造成的对比错觉。**先测，再猜。**

**这一轮最有价值的动作：反向验证。** 把 `UsingLibvpx` 强行置 false 重编，自检立刻挂 3 条
（`全透明 0/4096 个像素 —— alpha 整条丢了`）；改回来即全绿。
**能失败的测试才算测试** —— 否则只是又添了几条永远通过的装饰。

界面层面也出了对照图（各跑一次 `--shot-floating`，同一位置同一个角色）：
修复前是黑方块、修复后透明正常 → `outputs\对比_形象黑底修复前后.png`。

**处置**：用户跑的就是 `bin\Release\net8.0-windows\` 那个（桌面快捷方式指过去），
关掉占用实例 → 重新编译 → 重启即修复。**1.4.2 的便携包当时还没打**（等用户发话）。

**环境细节**：这台机器上跑编译前必须 `python tools/mkenv.py && source .tmp-env.sh`，
否则 NuGet 报 `MSB4018 path1`；`taskkill //PID` 在 bash 里会被转义吃掉，关进程用 PowerShell `Stop-Process`。

## 再修一次：用户报「颜色还是不对，像反色了，本来应该是蓝色」→ 版本 1.4.3

上一轮刚把黑底（alpha 丢失）修掉，用户紧接着报**颜色整个是错的**：
深蓝紫的头发显示成**栗棕红**、眼睛从蓝变橙。而且给了一条关键线索——
**「目前只有切换的时候开头几帧是对的」**。

**那条线索差点把方向带偏**：通道顺序这种错是**逐帧一致**的，不可能"开头对、后面错"。
于是先去查"逐帧累积的损坏"（帧边界漂移？环形缓冲被覆写？），
读了 `VideoDecoder.ReaderLoop` / `ReadExact` 才排除 —— 它是 `while (got < count)`
**读满一整帧**的，边界不会漂。

**真正的解释**：切换动作后那几帧**根本不是视频帧**，是 WPF 自己解码的**静态图**
（`whale.png`，那张是准的）；视频帧要等 ffmpeg 起来（≈150 ms）才贴上。
所以"开头几帧对"和"逐帧一致的通道错误"**并不矛盾** —— 是两段不同的东西。

**根因**：`-pix_fmt rgba` 吐的是 **R,G,B,A**；`SpritePlayer.PresentVideoFrame`
把它直接写进 **`PixelFormats.Bgra32`**，而 WPF 这个格式内存里是 **B,G,R,A**。
中间没有任何转换代码 —— **红蓝两条通道整个对调**。

**实测**（同一帧，raw 字节 vs ffmpeg 自己编码的 PNG）：

| 解读方式 | 最大差值 | 超阈值像素通道数 |
|---|---|---|
| 按 R,G,B,A | **0** | 0 ← 字节里确实是 rgba |
| 按 B,G,R,A | 125 | 76306 |

**界面级铁证**（同一张 `--shot-floating` 截图里数特定颜色）：

| 图 | 蓝紫 RGB(48,72,144) | 栗棕 RGB(144,72,48) |
|---|---|---|
| `whale.png` 静态图（基准） | 1160 | **0** |
| 修复前那张悬浮窗截图 | 1728 | **299** |
| 修复后 | 2027 | **0** |

同一张图里**静态图是蓝的、视频帧是棕的**，且 1728 + 299 = 2027（一像素不差地变回来）。
**上一轮把这张图里的角色描述成"棕发"时其实已经看到了 bug，只是误当成"不同姿势"放过去了。**

**修了三处**：

1. `VideoDecoder.cs`：`-pix_fmt` 从 `rgba` 改成 **`bgra`**（swscale 内部顺手就换，不额外花时间），
   提成 `public const string PixelFormat`，并加 `OffsetB/G/R/A` 常量让自检不硬编码数字。
   类头注释新增一节「像素字节序必须是 bgra（红蓝别弄反）」。
2. `SpritePlayer.cs`：在 `WriteableBitmap(..., PixelFormats.Bgra32, ...)` 上方写明
   **这两处是一对，改一边就必须改另一边**。
3. `DiagnosticsService.cs` + `tools/selftest`：同一段"左半纯红、右半透明"的测试素材
   正好拿来验通道序 —— 判据 `avgR > avgB + 60 && avgR > avgG + 60`。
   自检 +2 条（**208 项**）、自测 +2 条（**305 项**）。

**反向验证**（继续沿用上一轮的做法）：把 `PixelFormat` 强行改回 `"rgba"` 重编 ——
自测 **303 通过 / 2 失败**、自检 **1 项未通过**，报的正是
`✗ 红蓝通道没有互换：左半实心像素均色 R=0 G=0 B=253 —— 红蓝反了`。改回来即全绿。

**这一轮真正的教训 ——「解出来了」和「解对了」是两回事：**

- 1.4.2 之前的断言（帧数、每帧字节数）→ alpha 全丢时**全过**；
- 1.4.2 补的断言（有没有透明像素、有没有实心像素）→ 颜色全反时**全过**。

两次都是"**结构对了、内容错了**"。断言必须落到**画面内容**上（透明值多少、
**红值落在哪条通道**）。另外：**用户说的每一句现象都要当真**
（"像反色""开头几帧是对的"），那是定位的关键证据，不是修辞。

**顺带记一个操作教训**：用 `-stream_loop -1` 配 `-frames:v N` 做解码测试时，
ffmpeg 没按预期在第 N 帧停下，一路把临时文件写到了 **35 GB**。
以后测无限流不要靠 `-frames:v` 兜底，读完自己想要的帧数就主动杀进程。

## 新功能：把文件直接拖到小鲸鱼上就能归档 → 版本 1.4.4

用户提的需求：「可以直接把文件拖到悬浮窗上然后自动打开主页面并归档」。
当天实现 + 当天验证完，提交 `063b09f`。

**做了什么**：把文件（或文件夹）拖到桌面小鲸鱼身上松手 → 自动打开主面板 →
切到「文件归档」页 → 记到**今天** → 弹气泡回报（`已记入今天：新增 2`）。
归档链路完全复用 `FileIntakeService`（分类 / 版本判定 / 原文件保护一个字都不改），
悬浮窗只多做两件事：把主面板支起来并切页、把结果弹成气泡。
设置页加了开关 `AutoOpenMainWindowOnDrop`（默认开）—— ⚠️ 这个字段**本来就有**，
但以前只给状态栏加一句话、**从来没真打开过窗口**，这轮才让它名副其实。

**本轮唯一真正的难点：透明的地方接不住拖放。**

悬浮窗是 `AllowsTransparency="True"` 的层叠窗口，Windows 对这类窗口的命中测试是
**逐像素看 alpha** 的 —— alpha = 0 的像素上 OLE 拖放会**直接穿透**到下层窗口。
所以拖到鲸鱼**旁边**的空白处什么都不发生、而且**一个错都不报**；
鲸鱼本体（不透明像素）上却是好的 → 表现成"这个功能时灵时不灵"，极难归因。

**修法**：根 `Grid` 背景从 `Transparent`（alpha = 0）改成 **`#01000000`**（alpha = 1 的近透明黑）。
肉眼无差别，但命中判定从"透明"变成"不透明"，整块矩形都能接住拖放。
（`AllowDrop` 本来就是 `True`，改它没用。）提示层 `DropHint` 反过来设
`IsHitTestVisible="False"`，免得它自己把拖放吃掉。

**为什么这条断言测不出来**：`DragEventArgs` 的构造函数是 **internal**，造不出假事件 ——
处理函数全对、命中测试全错时，断言和自检都会"全绿"。所以补了两个真家伙：

- `tools/dragsource/`（C#，新增）：真实 OLE 拖拽源。在屏幕内的普通窗口里、
  **自己的 `MouseDown` 消息上下文里**发起 `DoDragDrop`，另起线程移光标并在目标点松开，
  带看门狗超时。⚠️ 按下点必须用 `PointToScreen` 算**屏幕物理坐标** ——
  拿 DIP 的 `Left/Top` 当屏幕坐标，在高 DPI 屏上会按到窗口外面，`DoDragDrop` **挂死不返回**
  （第一版就死在这）。
- `tools/drop_probe.py`（新增）：三场景 —— 拖到鲸鱼**旁边**的透明处（**该接住** ← 哨兵）、
  拖到鲸鱼**身上**（该接住）、拖到窗口**矩形外**（不该接住、不该开主面板）。
  判据只看「主面板开没开 + 文件进没进当天归档」两层；
  **不看 `DoDragDrop` 的返回值** —— 桌面本身也是合法拖放目标，`effect` 恒为 `Copy`，看它会假绿。

自检那一节**特意让它有牙**：为了验"**一律记到今天**"，探针会**先把主面板拨到昨天**再拖 ——
不先翻走的话主面板恰好就在今天，这条规则对不对根本测不出来。
日志里会并排写「拖入前主面板正在看：2026-09-19 → 现在是 2026-09-20」。

**顺手修掉一个老 bug**：`FileIntakeService.Expand` 过滤自己数据目录时前缀比较没补目录分隔符，
导致**名字以数据目录名开头的兄弟目录被整批静默跳过**。已修 + 加自测守着。
发现得很偶然：探针的测试文件造错了位置，现象是"接住了但归档 0 条"。

**这一轮的教训**：

- **"窗口接住了没有"和"处理函数对不对"是两回事。** 前者靠运行时环境（命中测试、DPI、
  模态循环）决定，只能真跑一次，而且**必须配一个反向验证**，否则"探针有牙"只是自欺。
- **透明的窗口不是"看不见的窗口"，是"没长在那儿的窗口"。** 它同时管视觉和命中测试，
  以后给悬浮窗加交互先问一句"这块像素是不是全透明"。
- **`DoDragDrop` 这类模态循环必须在"窗口自己收到鼠标按下"的消息上下文里发起**，
  "先合成按下再直接调"会卡死在模态循环里（`DragMove()` 同理）。

`Invalid URI: The format of the URI could not be determined`，**偶发崩溃**，
看着像随机闪退。为它写了半天诊断脚本才定位到。

### 1.4.4 收尾时补的三件事（同一天、同一提交线）

**1. 开关只掐了半个动作。** `AutoOpenMainWindowOnDrop` 第一版只把
`SwitchTo(NavPage.Files)` 包在开关里 —— 面板照样弹出来，与开关名字承诺的
"要不要打开主面板"对不上。改成：关掉时走
`App.ArchiveFromFloatingQuietlyAsync`（不进主面板、不创建窗口、只用气泡回报），
归档行为（走 `FileIntakeService`、记入今天）与开着时**一模一样**。
自检两边都验：开 → 面板出现且切到归档页；关 → 面板**根本没被创建**。
→ **开关的名字就是它的规格**，把它承诺的整段动作圈进去，然后开/关两边都验。

**2. 用户的 `settings.json` 里躺着 `"autoOpenMainWindowOnDrop": false`。**
这是 1.4.3 及以前写下的**死字段**值（当时没有任何代码读它）。
1.4.4 起它真的管事了，这时必须是"开"，否则用户拖完"什么都没发生"、
而配置文件里那一行看着毫无异常 —— 这种"新功能没生效"极难归因。
所以加了 `settingsRevision` 代次标记 + `SettingsService.Migrate()`：
第 1 代的文件强制打开这一项一次，**用户自己选过的值不动**（只认代次不认内容）。
自测 4 条钉着；**反向验证**：把 `Migrate()` 关掉重编 → 自测挂 2 条（正是迁移那两条）。
本机实测已迁移成 `true` / `"settingsRevision": 2`。

**3. 探针被环境骗了一轮。** 复跑 `tools\drop_probe.py` 时三个场景**一起**报
"看门狗超时、DoDragDrop 挂住"，差点当成回归 —— 实际是桌面被一个
**Blender 4.5.3** 窗口占满（`WindowFromPoint` 四个落点全返回它），
合成出来的左键送给了 Blender，拖放源窗口根本收不到 MouseDown。
（我**没有**去关用户的 Blender：那里面开着 `D:\licheng2026\...\92_7.blend`。）

- `tools/drop_probe.py` 新增 `guard_target()`：落点底下是**第三方**窗口 → 直接停下说清原因
  （`SystemExit 6`），**不报成失败**；底下是桌面则照常跑（那说明鲸鱼这块像素真没接住，正是要报的错）。
