# 2026-09-17

## 修「跨天再归档」的归属日期错位（版本 1.3.0 → 1.3.1）

### 用户报的现象

> 我在 9 月 16 归档的文件，9 月 17 再次归档的时候只在 9.16 的页面上有显示 v2。
> 9.17 当天的页面没有显示归档文件。

### 定位过程

先看真实数据（`%APPDATA%\WhaleLog\index.json`，**只读**）：5 条归档记录里
有两条正是这个形态 ——

| 文件 | 记录上的 `addedDate` | 历史里 v2 的 `recordedAt` |
|---|---|---|
| `92_3.blend` | 2026-09-16 | **2026-09-17 16:12** ← 用户报的这次 |
| `92_2.blend` | 2026-09-15 | **2026-09-16 17:20** ← 前一天也中过同样的招 |

人可读的 `notes\2026-09-16.md` 写着 `92_3.blend v2`（更新时间戳却是 09-17 16:12），
而 `notes\2026-09-17.md` 的 front matter 是 `files: 0` —— 现象在盘上直接可见。

根因：`FileIntakeService.IntakeOne()` 里「同一路径、内容变了」这一支
只改了 `Version`/`Sha256`/`LastWriteTime`，**从没动过 `AddedDate`**（`ApplyVersion` 里也没有）。
而全程序判断「某天有哪些归档文件」全都只看 `AddedDate`：当日页面、只看当天、
全部视图分栏、月历圆点、日报周报、`notes\*.md` —— 六个入口一个不落。
所以新版本永远粘在首次归档那天，产生它的那天反而是空的。

顺带发现的**不一致**：同一个「内容改了」的动作，
换路径归档会正确地记在今天（走"情况三"新建记录），
同路径归档却把日期留在过去 —— 仅因为路径相不相同，归属日期有两种行为。

### 修法（用户选的：两天各留一条，分开记 v1 / v2）

归档记录的粒度改成 **一个路径 × 一天 = 一条记录**：

- `LogBookStore` 新增 `FindFileByPathOn(path, date)`；
  `FindFileByPath` 改成返回该路径**最新**那条（判"内容变没变"要跟最近一次比）。
- `IntakeOne` 改成问「**今天**归档过这个路径没有」：
  - 今天归档过 + 指纹相同 → 重复（Duplicate）
  - 今天归档过 + 指纹不同 → 就地升版本（同一天不刷重复行）
  - 今天没归档过 → 新记一条，版本号接着版本链往下走
- `ApplyVersion` 增加 `dateKey` 参数，一并写 `AddedDate`/`AddedAt`；
  快照随即落到「这一版归档的那天」目录下。
- 类注释里写清了这条粒度规矩和"六个入口都看 `AddedDate`"，免得下次被改回去。

  同一天反复改只有一行、版本链 `[v1, v3]`、内容没变不多记一条、快照落在当天目录。

  5 → 7 条记录，`92_2` 拆成 `v1@9-15` / `v2@9-16`，`92_3` 拆成 `v1@9-16` / `v2@9-17`，
  days 数量不变、备份文件生成、写回后重新读校验通过。

### 待办（写这条日志时还没做）

**需要用户先退出正在运行的鲸记（PID 18080）**，然后：

1. 重建 Release + apphost（实例锁着 `bin\Release\WhaleLog.exe`，编不过去）。
2. 跑 `WhaleLog.exe --selfcheck --quiet`（隔离数据目录）确认 164 项全绿。
3. 对真实数据跑 `python tools\repair_archive_dates.py --apply` 修那两条历史记录。
   **这一步绝不能在程序运行时做** —— 它内存里的旧 book 一存盘就把修复覆盖了；
   修复脚本已经自带这道检查（运行中只预览、不写入）。
4. 重新打便携包（1.3.1）与交接包；notes 会在程序下次存盘时自动重新生成。

### 教训 / 值得记住的

- **一个字段同时喂六个入口，改它就等于改六个入口。** `AddedDate` 就是这样一个字段，
  单看某处代码完全看不出它的分量 —— 必须先全局 grep 再动手。
- **"同一个动作、两种行为"往往就是 bug 的指纹。** 换路径归档能正确记日期、
  同路径归档不能，这种不一致一出现就该顺着查下去。
- **改用户真实数据前先做副本演练，并且判据要写在脚本里。** 修复脚本默认只预览、
  检测到程序在运行就拒绝写入 —— 否则修好的一瞬间就会被内存里的旧数据覆盖，
  而且**看起来像是修复无效**，会把人带偏。
- 脚本第一版有个真 bug：保留了最新那天，却忘了把 `AddedDate` 改过去 ——
  正是要修的东西。**预览输出救了我一次**，所以预览这一步不能省。

### 收尾（用户退出实例后当天完成，1.3.1 已发货）

`--selfcheck` 164 项全过；`repair_archive_dates.py --apply` 把真实数据 5 → 7 条
（备份 `index.json.bak-20260917-163920`）；便携包 `鲸记 WhaleLog 1.3.1.zip` 与
交接包均已出并验证通过。

修工具时又踩两个坑，都是"换个面目出现"的类型：

- **`tasklist` 在中文 Windows 上输出 GBK。** `text=True` 按 UTF-8 硬解会抛
  `UnicodeDecodeError`，但抛在**读 stdout 的子线程**里，异常传不回主线程 ——
  只让 `.stdout` 变成 `None`，最后报成 `'NoneType' object has no attribute 'splitlines'`。
  看到这种错先怀疑子进程输出的编码。修法：`raw.decode("mbcs", errors="replace")`。
- **沙箱批量删除保护会拦 `shutil.rmtree`**（>50 个文件），并且**拦完脚本静默中断**，
  只留半截输出，看起来像"打包卡住了"。先把旧目录改名（`mv` 不算删除）即可绕开。
