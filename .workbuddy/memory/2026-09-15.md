## 1. 悬浮窗接入精灵图动画播放器

### 播放器的两个关键取舍

1. **时间由时钟算，不由"收到几次事件"算。** 每帧显示第几帧 = 已过时间 ÷ 单帧时长。
   渲染时钟约 64Hz，24fps 的动画落在 2~3 个 tick 上，靠计次会累积成明显的忽快忽慢。
2. **渲染时钟 + `DispatcherTimer` 双通道。** `CompositionTarget.Rendering` 在窗口不可见
   （被隐藏、会话锁定、远程桌面）时**根本不触发** —— 只挂它的话动画会永远卡在"正在播放"，
   后面所有动作都被堵住。两个通道都调同一个幂等的 `Advance()`，谁先到谁推进。

素材**按需解码**：帧表在扫描阶段就解析好（很便宜），真正的位图等第一次播到才解码，
没被用到的动作不占内存。一帧 720×720 的精灵图整张解出来约 16MB，
三个动作就是 50MB，没必要。

### 动作名与别名

目录名就是动作名，归一化后比对（大小写、下划线、连字符都忽略）：

| 动作 | 别名 | 触发时机 |
|---|---|---|
| `clickBounce` | `click` `tap` `poke` | 单击小鲸鱼（打开主面板时） |
| `blink` | `idle` `idleblink` `blinkidle` | 闲置随机 4~9 秒一次 |
| `alert` | `remind` `reminder` `notify` `warning` | 到点提醒；没有则退回原来的整体上下弹动 |

动作名撞车（`clickBounce\` 和 `Click-Bounce\` 同时存在）时，
**目录名与动作键完全一致的那份优先**，另一份记一条"重复"。
一开始按纯字母序排，赢的是 `Click-Bounce` —— 显然不是用户的意思，改成现在这样。

## 3. 换素材不能改变角色大小（最容易砸的一处）

静态形象是 610 画布塞进 168 的框、角色占 600 高 → 屏幕上 **165px**。
换成 720 画布的精灵图、角色还是 600 高，如果框仍留 168，角色只剩 **140px** ——
凭空小 15%，而界面上只表现为"好像小了点"，极难定位。

所以鲸鱼框高度按帧表反算：

```
框高 = 角色设计屏幕高度 × 帧高 ÷ 角色像素高 = 165 × 720 ÷ 600 = 198px
```

**窗口高度必须跟着一起变**（`ExpandedDesignHeight = 296 + (框高 − 168)` → 326）：
只把图放大不动窗口，多出来的 30px 会顶掉气泡的位置（星号行只剩 40px < 气泡需要的 63px）；
只把窗口放大不动图，鲸鱼脚下会多一条空白。

验证（离屏出图 + 逐行扫内容带）：装素材前后**角色在屏幕上都是 165px**，
窗口 296 → 326，多出来的 30px 全是透明画布余量。
静态形象（无 `anim\` 目录）时一切与改动前**逐像素一致**。

### 加了一个开关

`AppSettings.FloatingAnimations`（默认开），托盘菜单加了「小鲸鱼动画」。
素材是用户自己做的，画得不好、抖得厉害、或者不喜欢动，要有一条不用删文件的退路。
关掉后行为与改动前完全一致。

## 4. 修掉样例素材自己被裁的缺陷

`tools/check_anim_assets.py` 报「帧3（上）」：8 帧弹跳的**最高帧头顶落到 y=-15**，
越过画布边缘被裁掉十几像素。

根因：估算幅度时按"上边留了 60px 就能上移 60px"算，**漏算了纵向拉伸** ——
拉伸到 1.07 时角色高 642，光拉伸就把头顶顶到 y≈19，留给整体上移的额度只剩十几像素。

改成按「头顶位置」倒推每帧的垂直位移：

```
头顶 y = 661 − round(角色高 × 纵向缩放) + 垂直位移   必须 ≥ 2
```

最高帧改成「拉伸 1.07 + 上移 15px」→ 头顶 y=4。样例现在 13 项校验全绿。

**并且给生成脚本加了 `assert_headroom`**：写出文件**之前**逐帧打印离边余量，
不够就当场报错退出。这道关必须卡在生成端 —— 被裁的是头顶十几像素，
缩略图里看着一切正常，等程序里播起来才发现跳到最高点就少一截。

## 8. 悬浮态形象：鼠标移入换成闭眼版（发 1.3）

### 输入是什么，难在哪

用户丢来一张 `closeeye.png`：**1254×1254 的 JPG，纯白底，没有透明通道**。
悬浮窗是无边框透明置顶的，直接塞进去就是一个白方块。所以第一步是抠图。

同角色的睁眼版本是本体内的 `DSniang1.png`（610×610，贴画布右下）。

### 抠图方案：本地泛洪填充，不用云端模型

这张是**平涂插画 + 纯白底**，没有渐变阴影过渡。这种图用「从四边泛洪填充、
按阈值吃掉接近背景色的连通区域」比通用抠图模型更干净也更可控 ——
关键是内部那些白色区域（头饰、衣领）**必须保住**，泛洪从外围进不去那里，正好。

管道里没有 numpy，装了一版（隔离 venv：`binaries/python/envs/default`，
基础环境只有 PIL）。venv 是独立的，Pillow 也要重装。

### 一个决定性的意外发现

本来准备好要"对齐"两张图的，结果一比：**IoU 0.9895，最优平移量就是 dx=0/dy=0，
bbox 完全重合（45,10,610,610）**。也就是说这两张本来就是同一张画的差分，
只是分辨率差 2 倍。那就不用对齐，缩放到基准画布即可。

（所以"对齐"这一步不能省 —— 它的价值在于**确认能省**。）

### 产出：`tools/prepare_expression.py`

抠底 → 缩放到基准画布 → 两级搜索最佳平移（粗 2px 网格 + 精 1px）→ 打印 IoU。
以后加新表情差分直接用它，IoU ≥ 0.98 才算合格。

> 第一版的对齐搜索写歪了：把 `dx/dy` 累加到 `best` 里，多次迭代会串成错的偏移。
> 重写成「先按缩放定候选，再独立搜平移」就干净了。**累加式的爬山很容易自己骗自己。**

另一个自作聪明：本来每次都往输出目录写一张「对齐差异图」（红=本体多出/青=新图多出），
结果第一次就写进了 `Resources/Assets/` —— 素材目录里混进诊断图。改成 `--diff` 显式开启。

### 代码接法

- 素材位 `whale-hover`（`AssetCatalog` 新增），候选名 `whale-hover.png` / `closeeye.png` /
  `anim/closeeye.png`，**没配就安静回落**，悬浮毫无变化，不报错。
- `FloatingWindow` 加 `_stillImage` / `_hoverImage` / `_hovering`；
  移入移出在 `SetHovering()` 里切 `WhaleImage.Source`。
- **容易漏的一处**：切的时候必须同时把 `SpritePlayer.BaseImage` 也换掉。
  不然动画播完回落的是睁眼图 —— 鼠标还悬着，眼睛却睁开了。

### 自检怎么测的

`SimulateHover(bool)` 直接调真实的事件处理函数，**不去真移动用户的光标**。
断言用**引用相等**（`ReferenceEquals(WhaleImage.Source, _hoverImage)`）——
悬浮切换本来就是"整张换掉"，换成同一张图不会有任何视觉变化，引用相等正是该断言的东西。

自测 213 → **216 项**；诊断自检 154 → **164 项**（新增「悬浮态形象」一段 9 条断言）。

  → 指令里"路径别用中文"的说法改掉了，改成"实测中文可以"（不能传自己没验过的说法）。
- 自测 **216 项**；自检 **163 通过 0 失败**。原仓库是 164，差的那 1 项是**全局快捷键**那条 ——
  本机有鲸记实例在跑、快捷键被它占着，程序**有意跳过**并打印说明行，不是失败。

### 抓到一个静默失败的坑（这轮最值钱的发现）

自检第一次跑：**退出码 0、没有任何输出、日志也没生成**。查了一阵才明白：

```bash
WHALELOG_DATA_DIR="$PWD/.tmp-selfcheck"   # ← 这样写根本不工作
```

Git Bash 里 `$PWD` 是 `/c/Users/...` 这种 POSIX 风格路径，**.NET 不认**，
`AppPaths` 初始化失败 → 自检压根没开始跑。换成 `C:/Users/...` 立刻正常。

真正危险的是**失败方式太不显眼**：退出码 0、不报错、`--quiet` 下连提示都没有。
不查日志的人会直接下结论"自检通过"。
所以指令里写死了判定标准：**看日志文件生成了没有，不看退出码。**

（顺带确认：两次情形下**用户真实的 `settings.json` 都没被碰过**，
隔离机制本身是好的 —— 坏的只是"以为跑了"。）

### 又踩了同一个坑：并行 Edit 同一文件

改 `新设备继续指令.md` 时，同一条消息里发了两个 Edit，结果**第一处落盘、第二处丢了**。
这个坑在本会话里不是第一次了（实现阶段也栽过一次，`SizeFor` 漏改那次同源）。
**结论：改同一个文件必须串行 Edit。** 早记在案了，还是手滑。

## 10. 接 Git 远端：卡在权限和网络上（这轮没接成）

用户要「建一下仓库吧，顺便把仓库地址更新到指令里」。**仓库没建成**，两处硬限制：

1. **平台 GitHub 连接器没有建仓库权限** —— `create_repository` →
   `403 Resource not accessible by integration`。
   但它**有文件写权限**：往一个**不存在**的仓库写文件返回的是 `404`（不是 403），
   说明缺的只是"仓库还不存在"，权限本身够用。
   **这个差异以后可以用来区分「没权限」和「仓库不存在」，很实用。**
2. **本机 `git push` 根本没路** —— `api.github.com` 通（HTTP 200），
   但 **`github.com` 被代理拦**（`CONNECT tunnel failed, response 502`）。
   git 协议走的就是 `github.com`，所以本机推不上去，换机器才行。

于是改成**把路铺平**而不是硬做：`新设备继续指令.md` 第 6 节重写成照着做就行的四步 ——
网页建仓库（含"**别勾 README/gitignore/license**，勾了会和本地历史打架"这个坑）→
本地 push（含 PAT 怎么申请）→ 另一台 clone → 冲突怎么处理（含"认一台当主力、另一台只读"
这个省事方案）。

**约定地址**写进了文档（3 处）：`https://github.com/yangdong19961116-cyber/whalelog.git`，私有。
用户建仓库时取同名就直接能用；换名字或换账号，改那 3 处即可。
⚠️ **这是约定值，用户还没确认** —— 他要是用了别的名字，得回来改。

顺手把打包脚本 **`tools/make_transfer_zip.py` 入了库**（原来是临时脚本）。
交接包这件事以后还会做（用户有第二台设备），不该每次重写。指令里也补了"怎么重打一个包"。
